# Git 提交信息规范

生成提交信息时，必须遵循下面的规则。核心要求：**提交信息要详细、可追溯，禁止只写一句笼统的话**（如「更新代码」「修复问题」「优化一下」）。

## 1. 整体结构

```
<type>(<scope>): <一句话概述>

<变更背景 / 为什么要改>
<具体做了什么，分条列出>
<影响范围、注意事项、后续动作>

<可选：关联信息，如 Refs / Closes / Breaking Change>
```

- 标题（第一行）必填，正文（body）必填，二者之间空一行。
- 语言统一使用**中文**（代码标识符、文件路径、API 名称保持原文）。
- 标题不超过 50 个字符，正文每行建议不超过 72 个字符。

## 2. 标题行

格式：`<type>(<scope>): <概述>`

- `type`：必填，取值为下表之一。
- `scope`：强烈建议填写，表示受影响模块，按所在项目的实际目录/包名命名（如 `ui`、`api`、`auth`、`db`、`config`、`deps`）；跨模块改动可省略或写 `*`。
- 概述：动词开头，说明「做了什么」，不加句号，不使用「一些」「相关」「若干」这类模糊词。

| type | 含义 |
| --- | --- |
| feat | 新增功能 |
| fix | 修复 Bug |
| refactor | 重构（不改变外部行为） |
| perf | 性能优化 |
| style | 代码格式（空格、缩进、分号等，不影响逻辑） |
| docs | 文档变更 |
| test | 测试相关 |
| build | 构建系统或依赖变更 |
| ci | CI/CD 配置变更 |
| chore | 杂项（工具、脚本、配置等） |
| revert | 回滚提交 |

## 3. 正文要求（重点）

正文必须回答三个问题，缺一不可：

1. **为什么改**：问题现象、需求背景、触发原因（一句话即可，但必须具体）。
2. **改了什么**：分条列出关键改动，尽量带文件名 / 函数名 / 接口名 / 配置项。禁止只写「修改了 xxx 文件」。
3. **有什么影响**：行为变化、兼容性影响、需要同步修改的地方、验证方式或遗留问题。

写法建议：

- 使用 `-` 分条，一条一个改动点，不要把所有内容塞进一段。
- 涉及数据/接口变更时，写清字段、参数、返回值的前后差异。
- 涉及配置变更时，写清配置项名称与默认值。
- 修复类提交需写明根因（root cause），而不是只写「修复了报错」。
- 影响面小、简单改动也应至少写一条「改了什么」和一条「影响/验证」。

**反例（禁止）**

```
fix: 修复登录问题
```

**正例**

```
fix(auth): 修复 token 过期后登出跳转失败的问题

背景：token 过期时接口返回 401，但前端未清理本地凭证，导致用户停留在空白页。

改动：
- src/utils/request.ts：拦截 401 响应，清除本地 token 并触发重新登录流程
- src/pages/login：新增登录失效提示文案
- server/src/middleware/auth.ts：401 响应统一补充 errorCode 字段

影响：登录态失效后会跳转至登录页，需要同步验证移动端 H5 登录流程。
```

## 4. 简化场景

即使是单文件小改动，正文也不能为空，至少包含：

- 一条改动说明（改了什么）
- 一条原因或影响说明（为什么 / 影响范围）

## 5. 特殊标记

- **破坏性变更**：在正文最后单独写 `BREAKING CHANGE: <说明不兼容点与迁移方式>`。
- **关联需求/缺陷**：正文末尾写 `Refs: #123` 或 `Closes: #123`（有则写，无则不写）。
- **回滚**：使用 `revert:` 前缀，并注明被回滚的 commit hash 与原因。

## 6. 禁止事项

- 禁止空标题、空正文。
- 禁止使用「更新」「优化」「调整」「修改」作为唯一描述。
- 禁止在标题中堆砌多个不相关改动（一次提交尽量聚焦一件事）。
- 禁止编造未实际发生的改动、影响或关联单号。
- 禁止使用表情符号（除非用户明确要求）。
